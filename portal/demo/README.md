# Кабинеты портала

Канон этого дерева — репозиторий [`SinopticsAI/pharma_ui`](https://github.com/SinopticsAI/pharma_ui).
Деплой на `https://pharma.sinoptics.ru` — [`infra/README.md`](../../infra/README.md).

Три приложения работают на живом ядре: вход через Keycloak realm `pharma`
(публичный клиент `medmost-spa`, PKCE), данные и диалог интейка — на
`https://pharma-edge.sinoptics.ru`. Мока на боевых экранах нет.

Основной интерфейс — регуляторный кабинет. Единица работы в нём не «заявка со
статусом», а **кейс продукта с порядком работ**: в каждую работу можно войти,
увидеть состояние, приложить документы по чеклисту. Состояние работы не
хранится в браузере — оно проецируется из карты `M0`–`M12`, которую ведёт ядро.

Целевая архитектура описана в
[`pharma_cert/portal/view/06-frontendnoe.md`](https://github.com/SinopticsVit/pharma_cert/blob/main/portal/view/06-frontendnoe.md).

## Запуск

```powershell
cd portal\demo
corepack enable
# Если EPERM на Program Files: corepack enable --install-directory $env:LOCALAPPDATA\bin
pnpm install
Copy-Item .env.example .env
pnpm run dev      # :5175
pnpm run dev:cn   # :5173
pnpm run dev:ru   # :5174
```

| Адрес | Что открывается | Контур запроса |
| --- | --- | --- |
| `http://localhost:5175/` | Регуляторный кабинет, русский язык | `cn` |
| `http://localhost:5173/` | Кабинет производителя, основной язык 中文 | `cn` |
| `http://localhost:5174/` | Консоль оператора РФ | `ru` |

Порты фиксированы: именно они прописаны в redirect URIs клиента `medmost-spa`.
`pnpm run demo` собирает всё на `:4173` — этим удобно проверять сборку, но войти
там нельзя, пока порт не добавят в realm.

Первый запрос после входа — `GET /accounts/me`. Если пользователь realm есть, а
строки в `account_users` нет, кабинет покажет экран `account_not_linked`:
аккаунты заводит менеджер, саморегистрации нет.

Шрифт Inter подключается из пакета `@fontsource/inter`, без CDN.

## Порядок работ

Порядок строится от типа продукта в кейсе: лекарство или изделие. Общая часть — карточка продукта, её проверка и поиск в государственных реестрах. Дальше треки расходятся. Разделения протеза и оборудования у кейса нет: это свойство продукта, а не будущего удостоверения, поэтому изделие ведётся по треку оборудования.

| Код | Работа | Комментарий |
| --- | --- | --- |
| 0.1 | Карточка продукта | Поля распознал агент в диалоге интейка; здесь они на чтение, вместе с источником каждого значения |
| 0.2 | Проверка карточки | Формальные правила полноты, пограничная квалификация эскалируется юристу |
| 0.2.1 | Проверка в реестрах | Виджет реестра медицинских изделий и ГРЛС. Если запись найдена, новая подача не требуется |
| 0.3 | Досье производителя | Инструкция, техописание, модели, материалы, риски, ISO 13485, макеты этикеток |
| 0.3.1 | Класс риска, вид НКМИ, трек СИ | Для лекарства вместо этого — тип препарата и стратегия GMP |
| 0.4 | Перевод на русский | С обязательной медицинской редактурой |
| 0.5 | Легализация и мандат | Отдельные слоты по п. 87: доверенность, полномочия подписанта, 营业执照, площадка, товарный знак, ISO |
| 0.6 | Подбор лаборатории | Область аккредитации проверяется в реестре аккредитованных лиц |
| 0.7 | Договоры лаборатории и метрологии | Для оборудования — параллельно |
| 1 | Уведомление о ввозе образцов | ЕПГУ 610095, до отгрузки, пошлины нет. Не форма 630782 и не право продавать |
| 2 | Таможенное оформление образцов | Цель ввоза — государственная регистрация, не коммерция |
| 3, 3.1, 3.2 | Испытания, утверждение типа СИ, инспекция | Кабинет 630782 здесь ещё не нужен: прикладывать нечего |
| 4 | Заявление на регистрацию | ЕПГУ 630782. Следующий аппарат — новое заявление, союзный трек — услуга 613264 |
| 5 | Статусы, запросы и досылки | Кабинет заявителя Росздравнадзора |
| 6, 6.1 | После регистрации | Коммерческий ввоз и, при необходимости, маркировка |

Заблокированная работа не открывается, пока не закрыты её предшественники, и показывает, чего именно ждёт.

## Как работа получает состояние

Чеклисты, ссылки на государственные кабинеты и требования легализации — статическая копия права в `apps/web-portal/src/data/work-plans.ts`. Состояние приходит из карты кейса: каждой работе сопоставлен узел `M0`–`M12`, и статус выводится из него. Так карта и список задач не могут разойтись.

| Работы | Узел |
| --- | --- |
| 0.1, 0.2, 0.2.1, 0.3.1 | `M0` |
| 0.5 | `M1` |
| 0.3, 0.6, 0.7 | `M2` |
| 0.4 | `M3` |
| 1, 2 | `M4` |
| 3, 3.1 | `M5` |
| 3.2 | `M7` |
| 4, 5 | `M8` |
| 6 | `M9` |
| 6.1 | `M10` |

Узла нет в карте — работа не требуется по этому треку: инспекция `M7` для класса 1 в карту не попадает. Узлы `M6`, `M11` и `M12` отдельной работы в порядке не имеют и показаны на карточке кейса как узлы карты.

Кейс появляется только после того, как классификацию утвердят специалист и клиент: карту строит ядро в этот момент. Завести кейс из кабинета нельзя.

## Как устроено

```text
apps/web-portal      регуляторный кабинет: кейсы и порядок работ
apps/web-cn          кабинет производителя, ZH основной
apps/web-ru          консоль оператора РФ, только RU
packages/api-client  единственная точка выхода в ядро кабинета
packages/contracts   zod-схемы ответов Edge
packages/auth        вход через Keycloak, Authorization Code + PKCE
packages/ui          shadcn/ui для /cn/ и legacy CSS Modules для ru/portal
packages/i18n        каталог ZH/EN/RU и форматтеры
packages/domain      типы кейса, продукта, узла карты, документа, мандата
packages/mock        сид-данные прежнего демо, приложения его не импортируют
launcher             страница показа и режим «рядом»
scripts              проверка стоп-листа и демо-сервер
```

Стек: Vite, React 19, TypeScript strict, файловый TanStack Router и TanStack Query,
Tailwind + shadcn/ui, zod в `packages/contracts`, assistant-ui и `@xyflow/react`.
Кабинет `/cn/` уже на этом наборе; `web-ru` и `web-portal` пока на CSS Modules.

Клиент написан вручную по мапперам Edge: спецификация шлюза описывает маршруты и авторизацию, но не схемы тел, поэтому генерировать из неё нечего. Обновления в кейсе приходят опросом; поток событий добавится, когда появится нагрузка, и экраны от этого не изменятся.

## Каких каналов ещё нет

Экраны на месте, но показывают состояние канала, а не выдуманные данные:

| Экран | Почему пусто |
| --- | --- |
| Счета кейса | маршрута реестра счетов в API кабинета нет |
| Чат по кейсу | переписки по кейсу ядро не отдаёт; диалог интейка живёт на экранах компании и продукта |
| Лента аудита | маршрута нет |
| Сертификаты, сообщения на `/` | маршрутов нет |
| Сверка реестров | `GET /registry/search` в первой волне всегда возвращает пустой список: публичного поиска в нём ещё нет, только ссылка и кэш |

Аккаунт для инструментов агента кабинет пока подставляет сам заголовком `X-Pharma-Account`: в JWT его нет. Обход временный — [SinopticsAI/pharma-agent#1](https://github.com/SinopticsAI/pharma-agent/issues/1). По той же причине локаль диалога заголовком не уходит: шлюз разрешает не всякий заголовок, а лишний роняет preflight, поэтому агент отвечает на `zh`.

Документ прикладывается скрепкой в композере чата: файл становится вложением сообщения, а не отдельной загрузкой рядом с ним. Загрузка остаётся presigned-контрактом ядра (`upload-url` → `PUT` в хранилище → `confirm-upload`), поэтому до прогона CORS на бакете `pharma-dossier` браузер файл не отдаёт: вложение остаётся в композере, а причина видна над нитью. Прогон описан в [корневом README](../../README.md).

## Что кабинеты соблюдают

- Кабинет производителя не содержит маршрутов подачи. Реквизиты ЕСИА, УКЭП и МЧД ядро не отдаёт в контуре `cn` — их не скрывают, их не присылают. То же для корневого кабинета: он ходит с контуром `cn`.
- Источник истины по правам — сервер. Интерфейс прячет то, чего нет в маске полей и в правах личности, но решение принимает ядро: 403 — обрабатываемый ответ.
- Статус вносит человек и прикладывает артефакт. Без артефакта ядро статус не примет; от подачи и дальше требуются завершённый мандат и закрытый список моделей.
- Классификацию подтверждает специалист, затем клиент. Вариант, помеченный как недопустимый, показывается с объяснением, но выбрать его нельзя.
- Строка комиссии и строка третьей стороны — разные типы записи. Свернуть их в одну сумму нельзя.
- Статусы кодируются формой и подписью. Светофорных индикаторов нет; дедлайн и риск — единственное применение янтарного цвета.
- Значения из ядра не переводятся: наименование продукта в досье и в интерфейсе совпадает буква в букву. Локализуются только строки интерфейса.
- `pnpm run check:copy` роняет сборку на формулировках из стоп-листа [`portal/view/05-marketingovoe.md`](../view/05-marketingovoe.md) §7.

## Отступления от целевой архитектуры

| Отступление | Почему | Как будет в продукте |
| --- | --- | --- |
| Один origin, пути `/cn` и `/ru` | Так раздаёт шлюз статики, и путь корня сохранён | Разные origin, разные OAuth-клиенты и наборы scopes |
| Один клиент `medmost-spa` на три приложения | В realm он один | Отдельный клиент и набор scopes на приложение |
| Клиент API написан вручную | В спецификации шлюза нет схем тел | Генерация из OpenAPI, когда схемы появятся |
| Консоль РФ пишет строки в коде, без каталога | Приложение одноязычное по концепции | Так же: каталог нужен только кабинету производителя |
| `web-ru` и `web-portal` на CSS Modules | Мигрирует только `/cn/` | Tailwind + shadcn в тех же пакетах |
| Публичного сайта и калькулятора нет | Вне объёма этой волны | Отдельное приложение `web-public` |
| Идентификатор диалога держится в адресе | У ядра нет поиска сессии интейка по компании | Маршрут поиска сессии или ссылка на сущности |

## Проверка

1. `pnpm run check:copy`, `pnpm run lint`, `pnpm run typecheck` и `pnpm run test` — без ошибок.
2. Войти на `:5175`, `:5173` и `:5174`; после входа приходит `GET /accounts/me`.
3. Связанный пользователь: портфель пуст, если в базе нет кейсов, — это ответ ядра.
4. Несвязанный пользователь: экран `account_not_linked`, а не пустой кабинет.
5. Оператор вносит статус в консоли; кабинет производителя и работы на `/` видят его после обновления данных. Нужны два пользователя одного аккаунта: `operator` и `client`.
6. Клиент на `/` не видит формы ввода статуса и не получает реквизиты подписи в мандате.
7. Переключить язык кабинета на 中文 и EN, проверить, что заголовки и таблицы не обрезаны.
